# M6.1 Target Construction Design

**Issue:** #34, M6.1 Target construction (single portfolio)  
**Milestone:** M6, Minimal risk, paper execution, ledger and P&L  
**Status:** Approved design for Deliverable 0 implementation

## Purpose

M6.1 activates the first portfolio-specific authority after the
portfolio-neutral recommendation boundary. It consumes a bounded selected set
of accepted recommendations and one immutable portfolio-state snapshot, then
terminates exactly once with one of:

- an immutable portfolio-scoped absolute `TargetPosition`;
- an explicit `PortfolioNoChange`; or
- a typed `PortfolioConstructionRejected` outcome.

The authority stops at construction. A target is advisory and non-executable.
It does not approve risk, reserve exposure, create an order intent, simulate a
fill, update accounting, or imply that execution is permitted.

This design implements the narrow Deliverable 0 slice required by issue #34.
It preserves the Phase 07 meanings and extension seams without attempting the
full portfolio lifecycle described by the planning contract.

## Decisions

### Bounded recommendation aggregation

One construction obligation accepts a bounded recommendation set for one
target key. Supporting a set now is necessary to make reinforcing, opposing,
duplicate, and cancel-out behavior deterministic. A one-recommendation-only
API would defer the central aggregation seam and require redesign during M6.

The Deliverable 0 aggregation policy is a versioned signed sum:

- positive recommendations contribute positive indicative exposure;
- negative recommendations contribute negative indicative exposure;
- all contributing recommendations use the policy's declared exposure scale;
- summation uses checked fixed-point integer arithmetic;
- recommendation order does not affect semantic output or identity.

The policy is deliberately simple. It does not read risk limits, reservation
capacity, execution liquidity, balances, fills, ledgers, query models, UI
state, host time, or arbitrary stores.

### Scope is intrinsic to a recommendation

`TradeRecommendation` will carry the immutable scope already accepted by its
source `StrategyEvaluation`:

- `run_id`;
- `strategy_instance_id`;
- `listing_id`; and
- `canonical_instrument_id`.

`RecommendationAuthority` copies these values from the evaluation and includes
them in recommendation identity derivation. This closes the current M5-to-M6
gap without introducing a forgeable external recommendation/scope wrapper.

### Absolute target semantics

The aggregate signed exposure is a desired final exposure, not an order delta.
For a nonzero aggregate:

- `desired_exposure_units` is the signed absolute target;
- `current_exposure_units` comes from the immutable snapshot; and
- `explanatory_delta_units = desired - current` is checked and explicitly
  non-executable.

If desired exposure equals current exposure, the authority emits no-change.
If all actionable contributions cancel to zero, it also emits no-change and
leaves the current absolute exposure unchanged. Cancellation is not an
instruction to flatten an existing position.

### Explicit fail-closed terminal outcomes

Inputs that are semantically valid but require no portfolio change emit a
lineage-bearing `PortfolioNoChange`. Invalid, incompatible, ambiguous, or
unsafe inputs emit `PortfolioConstructionRejected`. Neither case silently
omits an accepted construction obligation.

## Public Contract

### Identity additions

The shared value-object registry gains opaque IDs for:

- `PortfolioId`;
- `AccountId`;
- `PortfolioSnapshotId`;
- `TargetPositionId`; and
- `PortfolioConstructionOutcomeId`.

They remain business-semantics-free 128-bit opaque IDs, consistent with the
existing contract registry.

### Target key

The Deliverable 0 `TargetKey` is single-listing and contains:

- portfolio ID;
- account ID;
- canonical instrument ID;
- listing ID; and
- target-policy version.

Direction is a value, not part of identity. Long and short proposals for the
same scope cannot evade netting or supersession by occupying different keys.

### Portfolio state snapshot

`PortfolioStateSnapshot` is immutable and contains:

- snapshot ID;
- run, portfolio, account, instrument, and listing scope;
- current signed exposure and decimal scale;
- snapshot run-input sequence and logical time;
- configuration epoch;
- completeness and freshness disposition; and
- whether the position is an explicitly configured paper-transition
  assumption.

M6.1 does not claim the snapshot is a ledger position. Until M6.6/M6.7 own
accounting facts, configured starting exposure must remain labelled as an
assumption.

### Construction policy

`PortfolioConstructionPolicy` contains:

- target schema, sizing, aggregation, and authority versions;
- the exact target key and run scope;
- allowed strategy instance IDs for this single portfolio;
- exposure scale;
- maximum selected recommendations, bounded by a compile-time ceiling;
- recommendation maximum logical age; and
- target validity duration.

The M6.1 sizing policy is identity sizing: accepted indicative exposure units
become target exposure units at the same scale. Capital allocation formulas,
weights, caps, floors, hysteresis, and cross-target allocation remain deferred
choices from the Phase 07 planning document.

### Construction cut

Each call supplies a deterministic construction cut:

- run-input sequence; and
- logical time in the replay logical clock domain.

Host wall time and call order are not semantic inputs.

### Terminal result

`PortfolioConstructionResult` exposes one failure-free terminal variant:

- `TargetPosition`;
- `PortfolioNoChange`; or
- `PortfolioConstructionRejected`.

Operational API misuse, such as an invalid authority configuration, returns a
typed construction failure without a terminal domain outcome. Once a valid
obligation is admitted, it receives exactly one terminal domain outcome.

`TargetPosition` includes:

- deterministic target and outcome IDs;
- target key and complete scope;
- desired absolute, current, and explanatory delta units;
- exposure scale;
- source recommendation and signal IDs in canonical order;
- snapshot identity;
- all policy versions;
- construction cut;
- validity end in logical time; and
- `downstream_risk_eligible = true` only for a constructed target.

No-change and rejection records include deterministic outcome identity,
stable reason, scope, snapshot/policy/cut references, and the selected or
excluded recommendation IDs needed to explain the result.

## Eligibility and Validation

The authority validates all of the following before constructing a target:

1. policy versions, bounds, duration, scale, target key, and assignment set are
   valid;
2. snapshot scope matches policy scope and the construction run;
3. snapshot is complete, fresh, ordered no later than the construction cut,
   and explicitly labels assumption-backed state;
4. recommendation count is within the policy bound;
5. recommendation and signal identities are unique;
6. each contributor is actionable, nonzero, scope-compatible, assigned to the
   portfolio, scale-compatible, issued no later than the construction cut, and
   still logically active;
7. all signed contributions, aggregate exposure, delta, validity arithmetic,
   and identity encoding are bounded and overflow-safe.

Hold recommendations are excluded from contribution. A hold-only or empty
selected set emits `NoActionableRecommendations`. Mixed hold/actionable input
may construct a target while retaining excluded hold IDs in the explanation
record. A duplicate, wrong-scope, unassigned, expired, or incompatible
recommendation rejects the complete obligation rather than being silently
dropped.

## No-Change Reasons

M6.1 defines stable reasons:

- `NoActionableRecommendations`;
- `ContributionsCancelled`; and
- `AlreadyAtDesiredExposure`.

Every no-change outcome is downstream-ineligible and carries the exact
construction key, cut, snapshot, policy versions, and recommendation evidence.

## Construction-Rejection Reasons

M6.1 defines stable reasons for:

- invalid, incomplete, stale, future, or scope-mismatched snapshot;
- recommendation capacity exceeded;
- duplicate recommendation or signal identity;
- recommendation scope mismatch;
- unassigned strategy;
- incompatible exposure scale;
- future-issued or expired recommendation; and
- arithmetic overflow.

These are portfolio-construction outcomes, not risk rejections.

## Determinism and Identity

Recommendations are canonicalized by recommendation identity before identity
derivation. Canonical encodings include a versioned domain separator and every
semantic input:

- run and target key;
- construction cut;
- snapshot identity and exposure;
- canonical recommendation/signal identity set;
- desired/current/delta amounts where applicable;
- terminal reason; and
- schema, sizing, aggregation, and authority versions.

Equivalent inputs produce equivalent target/outcome identities regardless of
input span order. Duplicate identities fail closed rather than being deduped.

## Module and Dependency Boundaries

Implementation lives in a dedicated `chronos_portfolio` C++ target under
`core/portfolio/` with a public API at
`chronos/core/portfolio/portfolio_construction.hpp`.

Allowed dependencies are:

- shared contracts and fixed-point/digest utilities;
- the immutable public recommendation API; and
- common build policy targets.

The target must not depend on risk, reservation, execution planning, adapters,
accounting, persistence implementations, telemetry exporters, applications,
or UI code.

## Testing

Tests are written first and must prove:

- positive and negative recommendations produce signed absolute targets;
- reinforcing recommendations sum deterministically;
- opposing recommendations net deterministically;
- complete cancellation emits explicit no-change without flattening current
  exposure;
- desired exposure equal to current exposure emits explicit no-change;
- empty and hold-only sets emit no-change and no target;
- input ordering cannot change semantic output or identity;
- duplicate recommendation and signal identities reject the obligation;
- wrong run, portfolio assignment, listing, instrument, account, strategy,
  scale, issue cut, validity, or snapshot state fails closed;
- all arithmetic boundaries reject overflow;
- target delta is explanatory and no M6.1 output is executable;
- target/outcome identity changes when any semantic input changes;
- M5 recommendation tests continue to prove exact signal cardinality and now
  prove copied scope lineage;
- the CMake authority boundary prevents portfolio code from acquiring risk,
  reservation, execution, adapter, accounting, storage, or telemetry
  capabilities.

The cumulative local gates remain `make m0-check` and
`make cpp-profiles-check`.

## Deferred Beyond M6.1

The following are deliberately not activated by issue #34:

- risk approval/modification/rejection, delivered by M6.2;
- serialized exposure and reservations, delivered by M6.3;
- paper intents and orders, delivered by M6.4/M6.5;
- ledger, positions, and P&L, delivered by M6.6/M6.7;
- durable target lifecycle persistence and recovery;
- active-target supersession state machines and downstream feedback snapshots;
- control admission for pause, stop, reset, policy activation, or assignment;
- multiple portfolios, accounts, sleeves, target keys, or capital allocation;
- weighted/latest-wins/strongest-signal policies;
- opportunity, multi-listing, multi-leg, venue-selection, or external-market
  resolution;
- operator-authored target entry; and
- UI/read-model/telemetry authority.

These omissions narrow Deliverable 0 implementation effort without weakening
the meaning of a recommendation, absolute target, no-change, construction
rejection, risk decision, reservation, intent, order, fill, or ledger entry.
